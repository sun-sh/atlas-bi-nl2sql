# 模型评测

## 当前评测集

`strict-model-v3-100` 是用于开发和回归的 100 条严格模型评测集；另有一套独立的 `strict-model-v3-holdout-30` 留出集，不参与 Prompt、口径和重试逻辑调整，用于观察未见组合上的表现。holdout 共 30 条，覆盖 4 类意图、7 种指标、时间与地区/渠道组合筛选、日趋势和 2 条连续追问；它仍属于固定电商业务域，不等同开放域泛化评测。

运行回归集：

```bash
python -m app.evaluation.run --suite regression --min-hit-rate 90
```

运行 holdout：

```bash
python -m app.evaluation.run --suite holdout --min-hit-rate 80 --output docs/evaluations/holdout-latest.json
```

两套题使用相同的严格模型路径、独立基准 SQL 和禁止规则回退约束，但不能把 holdout 的分数与回归集分数混在一起报告。

`strict-model-v3-100` 包含 **100 条严格模型回归用例**，覆盖固定种子的电商数据（2025-10-01 至 2026-02-28）。用例由时间窗口、地区、渠道、品类、销售额、商品销量、退款率、退款原因、退款金额、ROI、日趋势、组合筛选组成，并保留 11 条两轮连续追问链。完整执行最多处理 **111 个查询轮次**；每个轮次可能包含 SQL 生成、有限修复和结果解读请求。

矩阵使用四个时间窗口：上个月（2026-01）、本月（2026-02）、近 30 天（2026-01-30 至 2026-02-28）、近 90 天（2025-12-01 至 2026-02-28）。地区覆盖华东、华南、华北、西南；渠道覆盖 App、MiniProgram、小程序、Web、Douyin、抖音；品类覆盖运动鞋服、食品饮料、数码家电、美妆个护。100 条用例的 ID、问题和独立基准 SQL 由 `app/nl2sql/evaluation.py` 生成，测试会验证 ID 唯一、基准可执行且结果非空。

## 严格链路与自愈

每轮通过 Schema 召回、规划、模型 SQL 生成、AST 门禁、只读执行、模型修复和模型结果解读。评测固定使用 `allow_rule_fallback=False`，规则 SQL 和确定性摘要不能替模型通过。

当前自愈机制分为三层：

- **模型生成层**：对支持该参数的模型关闭 thinking，避免思考内容占满输出预算后 `content` 为空；首次空 SQL 会触发一次模型重试。
- **SQL 执行层**：SQL 语法、未知字段、危险语句和执行错误进入模型修复；修复仍受 `MAX_REPAIR_ATTEMPTS` 限制。全为空的聚合结果也会作为异常进入修复。
- **结果与解读层**：模型 SQL 执行成功后，用独立基准核对结果行数、维度集合、数值、排序和业务口径；解读流截断、为空或中断时最多重试一次，仍失败才在生产链路回退摘要，严格评测判失败。语义错误目前只能被评测发现，不能由通用运行时凭空推导出正确数值。

因此，“自愈”不能保证任意 SQL 语义都被修好。它可以修复有明确错误信号的 SQL；对于“能执行但算错了”的查询，必须依靠业务约束、独立验收器或模型二次审查。100 条评测的意义就是把这两类失败分开记录，而不是把规则结果伪装成模型成功。

## 判分规则

结果验收使用评测器内独立维护的只读标准 SQL，**不调用运行时规则 SQL 生成器**。标准查询只用于核对模型结果，不代替模型作答。验收检查：

- 完整行数、维度集合和唯一性。
- 每个分组的数值，绝对误差不超过 0.01；拒绝空值、布尔值和非有限数值。
- 题目要求的降序或日期升序。
- 中文和英文业务列别名，以及常见渠道别名。
- 可构建非空 grounded digest，且模型确实完成非空结果解读。

业务口径明确为：销售额和客单价只统计 `status='paid'`；订单主表品类销售额不能替代商品行品类销量；退款率为退款申请单数除以全部订单数；ROI 为已支付销售额除以投放花费，两张表先分别聚合再计算。

连续追问会先执行并验收前置问题，再把真实计划和上下文传给下一轮；前置问题失败时整条追问链失败。耗时和尝试次数包含前置轮次。

| --- | ---: | ---: | ---: | ---: | ---: |
| 首轮 | **79/100** | 100% | 88% | 32,545.6 ms | 1/1 |
| 最终轮 | **100/100** | 100% | 100% | 31,846.3 ms | 2/2 |

首轮 21 条失败中，12 条为模型解读问题，9 条为结果口径问题。修正 SQL 指令、业务口径、空 SQL/全空聚合/解读重试和验收逻辑后，同套件复跑达到 100/100：修复 21 条、回归 0 条。**21 条不能全部归因于运行时自愈**；完整闭环是评测发现问题 → 修正约束和重试逻辑 → 独立验收再评测。最终轮 2 条运行时 SQL 自愈均成功。

最终轮由 3 个隔离进程运行，报告保存 `runtime`、`source_sha256`、`case_manifest_sha256` 和 `evaluation_contract`。完整结果见 [首轮 JSON](evaluations/evaluation-v3-100-initial-2026-10-27.json) 与 [最终轮 JSON](evaluations/evaluation-v3-100-2026-10-27.json)。该成绩是带日期的在线能力快照，不是 CI 固定分数。

2026-11-03 的当前配置实时抽查为 **99/100**：`roi-channels` 首次 SQL 为空，导致该轮生成失败；单独复跑该用例时触发一次模型重试并通过。这个结果说明在线模型存在波动，归档的 100/100 不应被表述为稳定承诺。

2026-10-27 的旧版 18 条快照为 **5/18 通过、命中率 27.8%、SQL 执行率 55.6%、模型完成率 44.4%、平均每条 15.4 秒**。该结果用于定位 Qwen thinking、空 SQL、SQL 修复、语义口径和解读回退问题，不代表当前 100 条套件成绩；完整报告见 [旧版评测 JSON](evaluations/evaluation-v2-2026-10-27.json)。

页面不会自动运行评测，需点击提交评测任务。任务进入 SQLite 队列后由单执行槽领取，页面轮询进度；任务支持取消、重试和两次运行对比。提交任务通过 FastAPI `BackgroundTasks` 执行，其他排队任务需要显式 claim worker 继续消费；当前没有常驻分布式 worker。

指标定义：

- **模型通过率**：严格链路、独立结果验收和模型解读全部通过的用例数 / 100。
- **SQL 执行率**：完整用例的所有轮次均成功执行的用例数 / 100。
- **模型完成率**：完整用例的所有轮次均由模型生成或修复 SQL、并由模型解读的用例数 / 100。
- **平均响应时间**：每条完整用例耗时均值；追问包含前置轮次。

API 返回 `suite_version`、模型名、评测时间、汇总指标和逐用例 `id`、`setup_question`、执行状态、模型来源、尝试次数与失败原因。数据集接口为 `GET/POST /api/evaluation/datasets`，实验接口为 `GET/POST /api/evaluation/experiments`，反馈接口为 `GET/POST /api/evaluation/feedback`；任务接口为 `POST /api/evaluation/tasks`、`GET /api/evaluation/tasks`、`GET /api/evaluation/tasks/{id}`、`POST /api/evaluation/tasks/{id}/cancel`、`POST /api/evaluation/tasks/{id}/retry`；`GET /api/evaluation/compare?baseline=...&candidate=...` 返回通过数、通过率、执行率、平均耗时，以及新增修复和新增回归的用例。报告保存在被 Git 忽略的 `data/evaluation_tasks.db`；归档报告会作为只读历史任务导入。

## 评测中台

评测中台把一次运行视为一条可追踪、可复用的质量记录，而不是一个阻塞式 HTTP 请求：

- 创建任务时校验数据集、实验、模型和密钥；任务以优先级进入 SQLite 队列。
- 数据库原子领取保证只有一个执行槽；FastAPI BackgroundTasks 执行提交的任务并把进度写入 SQLite，页面每 3 秒轮询。
- 显式执行只处理提交的指定任务；其他排队任务由显式 claim worker 继续消费，避免误执行其他任务。
- 支持取消排队任务、对运行中任务发出取消信号，以及基于原任务重试。
- 完成后保存脱敏汇总、逐用例结果和运行元数据，不保存模型密钥。
- 任务历史包含运行时任务与 `docs/evaluations/` 归档任务。
- 数据集版本记录用例子集、数量和校验和，任务可按版本运行。
- 实验把同一假设下的多次模型运行组织在一起。
- 失败用例可进入 bad case 回流队列，记录分类和复核建议。
- 对比接口按用例 ID 计算 `新增修复`、`新增回归` 与指标差值。

这套能力是可运行的项目级评测中台，但仍不是跨组织评测平台：当前使用 SQLite 任务队列和单执行槽，没有分布式任务集群、跨租户权限、自动人工标注或线上抽样回流。

## 复现与离线回归

```bash
python -m pip install -r requirements-dev.txt
python -m app.evaluation.run
python -m pytest -q
node --check app/static/app.js
```

真实模型评测需先在 `/models` 保存并启用模型，会调用在线 API 并消耗模型配额。标准测试固定关闭在线模型和 BGE 下载，用真实本地数据和受控模型响应验证验收器、自愈边界和失败分类。CI 在 `LLM_ENABLED=false` 下运行模型评测冒烟检查，验证入口与未配置状态，不产生在线模型成绩；真实模型评测需手动执行并记录日期。
